# 01. Монорепозиторий на pnpm workspaces

## Что сделали

Собрали каркас монорепозитория, чтобы frontend, backend и общий код жили в одном репозитории и делили между собой типы и Zod-схемы без публикации в npm.

## Что и зачем

| Файл | Зачем нужен |
| --- | --- |
| `.gitignore` | Первым делом закрывает `private/` (резюме с личными данными), `.env`, `node_modules`, сборку |
| `.gitattributes` | В репозитории всегда LF, даже когда коммитишь с Windows |
| `.editorconfig`, `.nvmrc` | Единые отступы и версия Node 24 для всех редакторов и машин |
| `pnpm-workspace.yaml` | Говорит pnpm, где лежат пакеты, и хранит каталог общих версий |
| `package.json` (корень) | `private: true`, версия pnpm и команды на весь репозиторий |
| `tsconfig.base.json` | Общие строгие настройки TypeScript, пакеты их наследуют |
| `packages/shared` | Первый пакет. Сейчас там `API_PREFIX`, позже приедут Zod-схемы |

Команды:

```bash
npm install -g pnpm@12.16.1   # поставили сам pnpm
git init -b main
pnpm install                  # создал node_modules и pnpm-lock.yaml
pnpm typecheck                # tsc --noEmit во всех пакетах
pnpm build                    # tsc выплюнул packages/shared/dist
```

Почему именно так, и какие были альтернативы:

- **Монорепо против двух репозиториев.** Два репозитория заставили бы публиковать `shared` в реестр и согласовывать версии. Здесь изменение схемы и его использование на клиенте и сервере попадают в один коммит.
- **pnpm против npm и Yarn.** У npm workspaces плоский `node_modules` и фантомные зависимости (разберём ниже). Yarn справился бы, но pnpm строже и экономнее по диску.
- **Turborepo и Nx не берём.** Пакетов всего три. `pnpm -r` сам запускает скрипты в порядке зависимостей, кэш сборки пока не окупит ещё один инструмент.
- **`npm i -g pnpm` против Corepack.** `corepack enable` пишет в `C:\Program Files\nodejs` и просит права администратора, а из поставки Node 25+ Corepack убрали. Точную версию всё равно фиксирует поле `packageManager`.

Важный, преважный момент про TypeScript: pnpm поставил свежий **TypeScript 7.0.2**, это нативный компилятор. Инструменты, которые лезут во внутренний API компилятора (линтеры, плагины фреймворков), могут быть с ним ещё не совместимы. Если на шагах с NestJS, Next.js или ESLint что-то не заведётся, версию меняем одной строкой в каталоге. Спойлер: так и вышло, на шаге 02 откатились на TypeScript 6.0.3.

## Как это работает

### Сначала .gitignore, потом всё остальное

```bash
# ❌ так не работает
git init
git add .                     # private/cv/*.docx уже в индексе
git commit -m "init"
echo "private/" > .gitignore  # поздно: файл остался в истории
```

Дело в том, что `.gitignore` действует только на **неотслеживаемые файлы** (untracked files), то есть те, которых ещё нет в индексе Git. Простыми словами: уже закоммиченный файл Git продолжает отслеживать, и он лежит в истории, откуда его достанет любой, кто склонировал репозиторий. Удаление новым коммитом историю не чистит.

```bash
# ✅ сначала правило, потом проверка
git check-ignore -v private/cv/CV_Sobol_Fullstack_Engineer_RU.docx
# .gitignore:2:private/   private/cv/CV_Sobol_Fullstack_Engineer_RU.docx
```

`check-ignore` назвал правило, которое сработало, значит, можно коммитить. Кайф.

### Фантомные зависимости

```ts
// ❌ так не работает надёжно (npm, плоский node_modules)
// в package.json пакета нет lodash, он приехал как зависимость чужой библиотеки
import { debounce } from 'lodash'; // локально работает
```

**Фантомная зависимость** (phantom dependency) это пакет, который код импортирует, хотя не объявил его в своём `package.json`. Простыми словами: Node ищет `lodash` вверх по папкам `node_modules`, а npm поднял его наверх ради чужой библиотеки. Библиотека обновилась и перестала тянуть `lodash`, и твой импорт падает на ровном месте.

pnpm: «стоп, в корень пакета я кладу только то, что ты объявил».

```ts
// Упрощённая модель - не исходный код pnpm
const nodeModulesOfPackage = {
  // объявленная зависимость: это симлинк
  typescript: '→ node_modules/.pnpm/typescript@7.0.2/node_modules/typescript',
};

const virtualStore = {
  // а настоящие файлы лежат тут, в .pnpm, рядом со своими зависимостями
  'typescript@7.0.2/node_modules/typescript': 'hard link на файл в глобальном store',
};

// import 'lodash' не объявлен -> в nodeModulesOfPackage его нет -> ошибка сразу
```

Что с этим делает наш код: `packages/shared` объявил `typescript`, поэтому `tsc` доступен в его скриптах. Необъявленное импортировать не получится, ошибка вылезет сразу, а не в проде. Взяли и запомнили: **в pnpm пакет видит только то, что сам объявил**.

### Как пакеты находят друг друга

**Рабочее пространство** (workspace) это набор пакетов одного репозитория, которые pnpm устанавливает вместе. Простыми словами: pnpm читает `pnpm-workspace.yaml`, обходит `apps/*` и `packages/*` и связывает пакеты между собой симлинками.

```json
// ❌ так не работает: pnpm пойдёт искать версию в npm-реестре
{ "dependencies": { "@portfolio/shared": "0.0.0" } }
```

```json
// ✅ протокол workspace: бери только из этого репозитория
{ "dependencies": { "@portfolio/shared": "workspace:*" } }
```

Эту связку мы проверили руками: временно создали пакет `apps/_probe`, заюзали из него `API_PREFIX` и снесли пакет. Node вывел значение константы, а симлинк выглядел вот так:

```text
apps/_probe/node_modules/@portfolio/shared -> packages/shared
```

То есть это не копия, а ссылка на живую папку.

### Почему exports смотрит на dist, а не на src

```json
// ❌ соблазн: отдавать исходник без сборки
{ "exports": { ".": "./src/index.ts" } }
```

Next.js ещё можно попросить транспилировать такой пакет (`transpilePackages`). А вот скомпилированный NestJS запускает обычный Node, и тому пришлось бы исполнять `.ts` прямо в проде. Встроенное в Node удаление типов (type stripping) поддерживает не весь синтаксис TypeScript и типы не проверяет. Строить на этом прод хрупко.

```json
// ✅ наружу отдаём собранный JS и d.ts
{
  "exports": {
    ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" }
  }
}
```

Поле **`exports`** задаёт точки входа пакета. Простыми словами: на `import '@portfolio/shared'` Node и TypeScript смотрят сюда и берут указанный файл, а внутрь пакета мимо `exports` импортировать нельзя.

Плата за это одна: `dist` в `.gitignore`, поэтому после свежего клона сначала нужен `pnpm build`. Запомним это для CI и Docker.

### Каталог версий

**Каталог** (catalog) это список версий в `pnpm-workspace.yaml`, на который пакеты ссылаются словом `catalog:`. Простыми словами: при установке pnpm подставляет вместо `catalog:` версию из общего файла, поэтому у всех пакетов один и тот же TypeScript. Обновлять её нужно в одном месте.

## Ещё раз, что мы сделали

Сначала закрыли `private/` в `.gitignore` и проверили это через `git check-ignore`. Затем объяснили pnpm, где живут пакеты, и задали общие строгие настройки TypeScript. Потом создали `packages/shared`, собрали его в `dist` и временным пакетом убедились, что импорт через `workspace:*` реально работает. Сами `apps/web` и `apps/api` появятся на своих шагах, пока в монорепо один пакет. Погнали дальше.

## Вопросы на собеседовании

**Зачем монорепозиторий на таком маленьком проекте?**
Чтобы фронт и бэк использовали одни Zod-схемы и типы без публикации пакета, а изменение контракта проходило одним коммитом. Цена: чуть сложнее настройка сборки и Docker.

**Чем pnpm отличается от npm?**
npm поднимает зависимости в плоский `node_modules`, из-за чего появляются фантомные зависимости. pnpm кладёт в корень пакета только объявленное, в виде симлинков на `.pnpm`, а файлы хардлинками ссылаются на глобальный store. Поэтому он строже и занимает меньше места.

**Что будет, если закоммитить секрет, а потом добавить его в `.gitignore`?**
Файл останется в истории. Нужно считать секрет скомпрометированным, заменить его и при необходимости переписать историю, например через `git filter-repo`.
