# 06. Форма контактов: Zod, throttler, honeypot, Telegram и Playwright

## Что сделали

Сделали страницу контактов с формой: сообщение проверяется одной Zod-схемой на клиенте и сервере, сохраняется в базу и уходит уведомлением в Telegram. От спама защитились лимитом запросов и honeypot-полем, а весь путь проверили настоящим браузером через Playwright.

## Что и зачем

| Файл | Зачем нужен |
| --- | --- |
| `packages/shared/src/contact.ts` | Zod-схема, общая для фронта и бэка |
| `apps/api/src/common/zod-validation.pipe.ts` | Проверяет тело запроса этой схемой |
| `apps/api/src/contact/*` | Контроллер, сервис и отправка в Telegram |
| `apps/web/src/components/contact-form.tsx` | Форма на React Hook Form |
| `apps/web/src/lib/api/contact-api.ts` | Типизированная отправка из браузера |
| `apps/web/e2e/site.spec.ts` | Сквозные тесты в настоящем браузере |

Команды:

```bash
pnpm dev:api          # API
pnpm dev:web          # сайт
pnpm test:browser     # Playwright, нужны база с seed
```

Настройки в `apps/api/.env`, всё необязательное:

```bash
CORS_ORIGIN=http://localhost:3000   # откуда браузеру можно отправлять форму
TELEGRAM_BOT_TOKEN=                 # выдаёт @BotFather
TELEGRAM_CHAT_ID=
```

Почему именно так, и какие были альтернативы:

- **Запрос из браузера в API против Server Action.** Через Server Action не нужен CORS, зато для API все посетители были бы одним IP сервера Next. Один спамер исчерпал бы лимит за всех. Цена прямого запроса: настройка CORS и публичный адрес API.
- **Свой `ZodValidationPipe` против `nestjs-zod`.** Это 15 строк, а новая зависимость ради них не окупается.
- **Honeypot плюс лимит против капчи.** Капча раздражает человека, которого мы хотим услышать, и для портфолио избыточна. Цена: упорного бота это не остановит, но лимит ограничит ущерб.
- **Playwright уже сейчас.** Unit-тесты не видят CORS, гидрацию и реальную отправку. Форма первая часть сайта, где это важно.

## Как это работает

### Одна схема на клиенте и сервере

```ts
// ❌ правила продублированы, и однажды они разойдутся
// на клиенте
if (name.length < 2) setError('Минимум 2 символа');
// на сервере
if (body.name.length < 3) throw new BadRequestException();
```

**Zod** описывает форму данных объектом, который существует в рантайме. Простыми словами: `safeParse` проверяет значение и возвращает либо очищенные данные, либо список ошибок, а `z.infer` выводит из той же схемы TypeScript-тип.

```ts
// ✅ packages/shared/src/contact.ts
export const contactMessageSchema = z.object({
  name: z.string().trim().min(2, 'Укажите имя: минимум 2 символа'),
  // ...
});
```

Важный, преважный момент: **проверка на клиенте это удобство, а проверка на сервере это защита**. Запрос можно отправить и мимо формы, через `curl`, поэтому сервер проверяет всё заново.

На сервере схему применяет пайп (pipe). Простыми словами: это класс с методом `transform`, через который Nest пропускает значение перед вызовом метода контроллера.

```ts
// Упрощённая модель - не исходный код NestJS
async function handleRequest(req) {
  await guard.canActivate(req);             // ThrottlerGuard: не превышен ли лимит
  const body = pipe.transform(req.body);    // ZodValidationPipe: бросит 400
  return controller.submit(body);           // сюда приходят уже чистые данные
}
```

Отсюда следствие: guard стоит раньше пайпа, поэтому неверные запросы тоже расходуют лимит.

DTO-класс при этом остался: типы TypeScript в рантайме стираются, а Swagger нужен класс. Проверка в Zod, контракт в DTO.

### CORS

```ts
// ❌ в браузере так не работает без настройки
fetch('https://api.example.com/api/v1/contact', { method: 'POST', body });
// Браузер: стоп, это другой origin, и сервер его не разрешил
```

**CORS** (Cross-Origin Resource Sharing, совместное использование ресурсов между источниками) это механизм, которым сервер сообщает браузеру, каким сайтам можно читать его ответы. Простыми словами: перед таким POST браузер сам отправляет запрос `OPTIONS` и смотрит на заголовок `Access-Control-Allow-Origin`. Нет разрешения, значит, основной запрос не уйдёт.

```ts
// ✅
app.enableCors({ origin: 'https://сайт', methods: ['POST'] });
```

Запомни ловушку: это защита **браузера**, а не сервера. `curl` на CORS плевать, поэтому от спама он не защищает. Для этого нужны лимит и honeypot.

Мы проверили это настоящим браузером: открыли сайт с запрещённого адреса, и форма показала ошибку, а запись в базе не появилась. Вторая ловушка: `localhost` и `127.0.0.1` для браузера это **разные** origin.

### Лимит запросов

`ThrottlerGuard` считает запросы с одного IP в окне времени.

```ts
// Упрощённая модель - не исходный код @nestjs/throttler
const hits = new Map<string, number[]>();

function canActivate(req) {
  const now = Date.now();
  const recent = (hits.get(req.ip) ?? []).filter((t) => now - t < ttl);
  if (recent.length >= limit) throw new HttpException('Too Many Requests', 429);
  hits.set(req.ip, [...recent, now]);
  return true;
}
```

Здесь две вещи, которые стоит запомнить:

- **Счётчик лежит в памяти процесса.** Перезапуск его обнуляет, а при нескольких экземплярах у каждого свой. Для одного сервера портфолио это нормально, иначе понадобился бы Redis.
- **За прокси IP будет чужой.** На хостинге запрос приходит через балансировщик, и без настройки у всех будет его адрес, то есть один общий лимит. На шаге с деплоем обязательно настроим `trust proxy`. Доверять `X-Forwarded-For` без прокси нельзя: подделать этот заголовок может кто угодно.

### Honeypot

**Honeypot** (приманка) это поле, которое человек не видит, а бот заполняет, потому что заполняет всё подряд.

```tsx
// ❌ бот выучит это за минуту, да и ошибка подскажет ему, что делать
<input name="website" style={{ display: 'none' }} />
if (body.website) throw new BadRequestException('Вы бот');
```

```tsx
// ✅ поле просто за экраном, с клавиатуры недоступно, от скринридера скрыто
<div aria-hidden="true" className="absolute -left-[9999px]">
  <input {...register('website')} tabIndex={-1} autoComplete="off" />
</div>
```

```ts
// ✅ отвечаем как при успехе и ничего не делаем
if (website) return;
```

Бот видит обычный ответ `204` и не понимает, что его раскрыли.

### Telegram не должен ронять форму

```ts
// ❌ сообщение уже в базе, а пользователь увидит ошибку и отправит его ещё раз
await prisma.contactMessage.create({ data });
await telegram.send(data); // Telegram лежит, вылетела ошибка -> ответ 500
```

База это главное, уведомление вторично. Поэтому `TelegramService` ошибок не бросает, а пишет их в лог и ждёт ответа не дольше 5 секунд.

Ещё три тонкости, и каждая закреплена тестом:

- **Токен сидит в адресе запроса**: `https://api.telegram.org/bot<token>/sendMessage`. Текст сетевой ошибки может попасть в лог вместе с ним, поэтому логируем только `error.name`.
- **Лимит Telegram 4096 символов**, а форма принимает 5000. Без обрезки длинное сообщение получило бы ошибку 400, и уведомление тихо потерялось бы.
- **Без `parse_mode`.** Текст пишет посторонний человек. С разметкой случайный символ `_` мог бы сломать отправку, а так это просто текст.

### Honeypot и лимит в e2e-тестах

В API-тестах настоящий `TelegramService` подменяется через `overrideProvider`, чтобы тесты не слали сообщения. Приложение создаётся на каждый тест заново, потому что счётчик лимита живёт в его памяти. Записи помечены своим доменом и удаляются после теста.

### Playwright: настоящий браузер

**Playwright** запускает настоящий Chromium и управляет им как пользователь. Простыми словами: тест работает в отдельном процессе Node и по протоколу отдаёт браузеру команды «открой», «заполни», «нажми», а тот реально делает запросы и выполняет JS.

```ts
// ✅ весь путь от кнопки до строки в базе
await page.getByLabel('Имя').fill('Анна');
await page.getByRole('button', { name: 'Отправить' }).click();
await expect(page.getByRole('status')).toContainText('Сообщение отправлено');

const { rows } = await client.query('SELECT ...', [EMAIL]);
expect(rows).toEqual([{ name: 'Анна', /* ... */ }]);
```

Поле `webServer` в конфиге сам поднимает API и сайт, причём API получает пустой токен Telegram, чтобы тесты не слали настоящих уведомлений. Сайт в тестах идёт через `next dev`: сборке нужен уже работающий API, а Playwright запускает серверы одновременно. Сценарий для продакшен-сборки разберём на шаге с CI, пока мы прогнали его вручную.

## Ещё раз, что мы сделали

Описали сообщение Zod-схемой в общем пакете и заюзали её и в форме, и на сервере. API проверяет запрос, сохраняет сообщение и старается отправить уведомление, не роняя ответ при сбое Telegram. От спама защищаемся лимитом с одного IP и honeypot-полем. Браузеру разрешили обращаться к API только с адреса сайта. В конце подключили Playwright и прошли весь путь от кнопки до базы. ## Вопросы на собеседовании

**Защищает ли CORS от спама?**
Нет. CORS это правило, которое соблюдает браузер. Прямой запрос через `curl` пройдёт на сервер без всяких проверок CORS. От спама защищают лимит запросов и honeypot.

**Почему бот с заполненным honeypot получает успешный ответ?**
Ошибка подсказала бы ему, что поле ловушка, и он бы перестал его заполнять. Успешный ответ не даёт ему такой информации.

**Что будет, если Telegram недоступен?**
Сообщение уже сохранено в базе, пользователь получает успех, а ошибка пишется в лог. Уведомление в этом случае пропадёт, но сообщение останется в базе и будет видно в админке v2. Если нужны гарантии доставки, понадобится очередь с повторами, для портфолио это избыточно.
