# 10. Деплой: Railway, Vercel и README

## Что сделали

Подготовили проект к выкладке: прод-образ API сам применяет миграции, лимит запросов видит настоящий IP клиента за прокси, а README объясняет архитектуру и порядок деплоя.

## Что и зачем

| Файл | Что изменилось |
| --- | --- |
| `Dockerfile` | Этап `migrate` убран, этап `api` теперь последний и содержит openssl |
| `compose.yaml` | Сервис `migrate` запускает прод-образ API командой `node --run db:release` |
| `apps/api/package.json` | Скрипт `db:release`, `prisma` и `dotenv` переехали в `dependencies`, в `files` добавлены миграции |
| `apps/api/src/database/` | Сюда переехал seed, теперь он компилируется в `dist` |
| `apps/api/src/contact/client-ip-throttler.guard.ts` | Лимит считается по настоящему IP клиента |
| `apps/web/vercel.json` | Сборка сайта вместе с `packages/shared` |
| `apps/web/public/cv/` | Публичное резюме без даты рождения, гражданства и юрлица заказчика |
| `README.md` | Запуск, архитектура, обоснование решений, деплой |

Почему именно так, и какие были альтернативы:

- **Pre-deploy команда против отдельного сервиса миграций.** Отдельный сервис на Railway никак не связан по порядку запуска с API, и новая версия могла бы стартовать раньше миграций. Pre-deploy выполняется до старта новой версии и останавливает деплой при ошибке.
- **Настройки в панели Railway против `railway.json`.** Документация Railway помечает `railway.json` как устаревший: такие файлы перестают читаться 2026-12-01. Замена, `.railway/railway.ts`, требует новый пакет и отдельный запуск `railway config apply`. Для одного сервиса это лишнее, поэтому настройки живут в панели, а их список записан в README.
- **`X-Real-IP` против `trust proxy`.** Стандартный путь Express это `trust proxy` и `X-Forwarded-For`. Но в документации Railway описан именно `X-Real-IP`, а поведение `X-Forwarded-For` там не описано. Опираемся на то, что описано.
- **Цена.** Образ API вырос с 511 до 790 МБ, потому что теперь внутри CLI Prisma. Зато исчез отдельный образ `migrate` на 2,5 ГБ.

## Как это работает

### Откуда на проде берутся таблицы

Первая мысль: выполнить миграции при старте приложения.

```ts
// ❌ миграции при старте API
await runMigrations();
await app.listen(port);
```

Два экземпляра стартуют одновременно и применяют миграции наперегонки, а упавшая миграция превращает деплой в бесконечный перезапуск.

Railway говорит: дай мне команду, я выполню её между сборкой и запуском. **Pre-deploy command** (команда перед развёртыванием) запускается один раз в отдельном контейнере, с переменными сервиса и доступом к приватной сети. Простыми словами: образ уже собран, новая версия ещё не запущена, а база доступна. Команда вернула не ноль, и деплой останавливается, а старая версия продолжает отвечать. Взяли и запомнили.

```json
"db:release": "prisma migrate deploy && node dist/database/seed.js"
```

**`migrate deploy`** применяет только готовые файлы миграций и никогда не сбрасывает базу. `migrate dev` на проде заюзать нельзя: он может предложить сброс данных и создаёт новые миграции.

### Почему `node --run`

В прод-образе нет pnpm, и это специально. А искать бинарник `prisma` руками неудобно.

```bash
# ❌ в образе нет pnpm
pnpm db:release
# ✅ Node 24 сам читает scripts и добавляет node_modules/.bin в PATH
node --run db:release
```

### Почему seed переехал в `src`

Раньше seed запускался через `tsx` из папки `prisma`. Тащить `tsx` в прод ради одного файла незачем.

```text
❌ prisma/seed.ts → нужен tsx в проде
✅ src/database/seed.ts → nest build → dist/database/seed.js → обычный node
```

Важный, преважный момент: seed полностью заменяет контент при каждом деплое. В v1 это фича, потому что контент живёт в `seed-data.ts`. Сообщения из формы он не трогает. В v2 админка начнёт менять контент в базе, и seed из релиза придётся убрать.

### Почему Railway соберёт именно API

Для Docker Compose мы указываем `target: api`. В документации Railway настройки цели сборки мы не нашли, а без цели Docker собирает последний этап.

```dockerfile
FROM deps AS web
# ...
FROM node:24-slim AS api # ✅ последний этап: его и получит Railway
```

Если поменять этапы местами, Railway молча соберёт сайт, и healthcheck упадёт. Поэтому в Dockerfile об этом есть комментарий.

### Какой IP видит лимит запросов

На шаге 06 мы сказали throttler: считай запросы по `req.ip`. Локально это работает. На Railway перед приложением стоит прокси.

```ts
// Упрощённая модель - не исходный код @nestjs/throttler
const key = req.ip; // за прокси это адрес прокси, один на всех
hits[key] += 1; // пять сообщений разных людей, и шестой получает 429
```

Railway передаёт адрес клиента в заголовке `X-Real-IP`. Наивный вариант верит ему всегда:

```ts
// ❌ клиент без прокси подставит любой адрес и обойдёт лимит
const key = req.headers['x-real-ip'] ?? req.ip;
```

Заголовок может прислать кто угодно, поэтому верить ему можно, только если его выставляет сам прокси. Чтение включается явно:

```ts
// ✅ TRUST_X_REAL_IP=true задаём только на Railway
const useHeader =
  process.env['TRUST_X_REAL_IP'] === 'true' &&
  typeof realIp === 'string' &&
  realIp !== '';
return super.getTracker(useHeader ? { ...req, ip: realIp } : req);
```

Оба поведения закрыты e2e-тестами. Чего они не доказывают: что прокси Railway перезаписывает присланный клиентом заголовок. Документация этого не говорит, поэтому проверять надо на настоящем домене: отправить лимит запросов с разными `X-Real-IP`, и следующий должен получить 429.

### Курица и яйцо между сайтом и API

Сборке сайта нужен работающий API, а API в `CORS_ORIGIN` нужен адрес сайта.

```text
1. Railway: база, API, домен. CORS_ORIGIN пока не важен: контент читает сервер Next.js
2. Vercel: API_URL и NEXT_PUBLIC_API_URL → сборка → адрес сайта
3. Railway: CORS_ORIGIN = адрес сайта → форма заработала
```

CORS проверяет только браузер, поэтому серверная сборка Next.js проходит без него. Кайф: разрывать цикл можно именно в этом месте.

### Что показал настоящий деплой

Настройки сошлись не сразу, и вот что пришлось поправить по факту:

- **Builder.** Панель Railway показала Railpack по умолчанию, поэтому Dockerfile выбрали явно.
- **`PORT`.** Задали `3001` явно, чтобы порт приложения и порт домена точно совпали.
- **Vercel.** Сборка прошла с первого раза: Root Directory `apps/web`, Next.js, `API_URL` и `NEXT_PUBLIC_API_URL`.

Проверили на живых адресах:

```text
страницы сайта и резюме          200, в PDF нет личных данных
кэш страницы                     X-Vercel-Cache: HIT
API, Swagger, база               200, seed применён
CORS с чужого адреса             заголовок разрешения не выдан
форма с сайта                    запись появилась в contact_messages
запросы с разными X-Real-IP      пятый запрос за час получил 429
```

Важный, преважный момент про последнюю строку: все запросы шли с одной машины, но с разными подделанными заголовками, и лимит всё равно сработал. Значит, прокси Railway подделку не пропускает. Чего эта проверка не доказывает: что два настоящих посетителя с разных адресов получают отдельные счётчики. Для этого нужен второй источник запросов.

Научили лимит запросов читать `X-Real-IP` по явному флагу. Написали README и порядок деплоя. Настройки Railway оставили в панели, потому что `railway.json` доживает последний месяц. Потом выложили всё по-настоящему и проверили на живых адресах. Кайф: проект теперь открывается не только у тебя на машине.

## Вопросы на собеседовании

**Как ты применяешь миграции при деплое?**
Pre-deploy командой до старта новой версии: `prisma migrate deploy`, а не `migrate dev`. Если миграция упала, новая версия не запускается. Миграции должны быть совместимы со старым кодом, потому что какое-то время он работает уже с новой схемой.

**Почему `req.ip` за прокси может сломать rate limiting?**
Приложение видит адрес прокси, и все клиенты попадают в один счётчик. Но и слепо верить заголовку нельзя: его может подделать клиент. Заголовок читаем только за прокси, который сам его выставляет.

**Почему CORS не мешает сборке сайта на Vercel?**
CORS применяют браузеры. Сервер Next.js обращается к API без этой проверки, поэтому контент собирается и без нужного `CORS_ORIGIN`. Браузеру он нужен только для формы контактов.
