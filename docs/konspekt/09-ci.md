# 09. CI: проверка каждого изменения в GitHub Actions

## Что сделали

Описали workflow, который на каждый push в `main` и каждый pull request проверяет чистую копию проекта: линт, типы, тесты, браузер и сборку Docker.

## Что и зачем

Файл один: `.github/workflows/ci.yml`. В нём три независимых задания (job):

| Задание | Что проверяет |
| --- | --- |
| `checks` | Линт, форматирование, типы, unit-тесты |
| `e2e` | Настоящая PostgreSQL, миграции, e2e API, контракт, Playwright на продакшен-сборке |
| `docker` | `docker compose up` действительно поднимает весь проект |

Почему именно так, и какие были альтернативы:

- **GitHub Actions против GitLab CI или Jenkins.** Код живёт на GitHub, настройка лежит в репозитории, и для открытых репозиториев это бесплатно.
- **Три задания против одного длинного.** Задания идут параллельно, а по названию сразу видно, что сломалось. Цена: установка зависимостей повторяется, это смягчает кэш pnpm.
- **Деплоя здесь нет.** Он появится отдельным шагом.

## Как это работает

### Зачем CI, если всё работает локально

Локально у тебя лежат `.env`, `dist` и сгенерированный клиент Prisma. Сборка может держаться на них, а ты об этом не узнаешь.

```text
❌ «У меня работает»
   на машине остался .env или старый dist, в репозитории их нет,
   а коллега после git clone получает ошибку
```

**Непрерывная интеграция** (Continuous Integration) это автоматическая проверка каждого изменения на чистой машине. Простыми словами: GitHub поднимает новую виртуальную машину, клонирует репозиторий и по очереди выполняет шаги из YAML. Шаг вернул ненулевой код, и задание падает.

### Из чего состоит workflow

```yaml
# Упрощённая модель, чтобы увидеть структуру
on: [push, pull_request] # когда запускать
jobs: # задания идут параллельно, каждое на своей машине
  checks:
    runs-on: ubuntu-latest
    steps: # шаги идут по очереди
      - uses: actions/checkout@v7 # готовое действие: склонировать репозиторий
      - run: pnpm lint # обычная команда в shell
```

Запомни разницу: `uses` подключает готовое действие, а `run` выполняет команду.

```yaml
permissions:
  contents: read
```

Это **принцип наименьших привилегий** (least privilege). Простыми словами: токен, который GitHub выдаёт заданию, может только читать код. Даже если зависимость окажется вредоносной, запушить в репозиторий она не сможет.

### База в CI

```yaml
services:
  postgres:
    image: postgres:18-alpine
    options: >-
      --health-cmd "pg_isready -U portfolio -d portfolio"
```

**Сервисный контейнер** (service container) GitHub запускает рядом с заданием и ждёт его проверку здоровья. Простыми словами: это настоящая PostgreSQL той же версии, что и локально. Моки базы не нужны.

### Как собрать сайт, которому нужен API

Ты уже знаешь проблему: сборке Next нужен работающий API. В CI шаги выстроены в нужном порядке:

```yaml
- name: Start API
  run: |
    nohup node dist/main.js > api.log 2>&1 &
    curl --fail --retry 30 --retry-connrefused http://127.0.0.1:3001/api/v1/health
- name: Build and start web
  run: |
    pnpm --filter @portfolio/web build
    nohup pnpm --filter @portfolio/web start ... &
```

Важный, преважный момент: `&` запускает процесс в фоне, а `curl --retry` ждёт его готовности. Без этого следующий шаг стартовал бы раньше, чем поднялся сервер.

```ts
// ❌ на шаге 06 Playwright сам запускал серверы и мог сделать только next dev
// ✅ теперь серверы уже работают, а reuseExistingServer: true их подхватывает
webServer: [{ url: WEB_URL, reuseExistingServer: true /* ... */ }];
```

Так браузерные тесты в CI идут по продакшен-сборке, а это именно то, что увидит пользователь.

### Контракт тоже проверяется

Шаг e2e сверяет `openapi.json` с кодом. Поменял DTO и забыл `pnpm gen:api`? CI упадёт, и фронт не разойдётся с бэком незаметно.

### Как мы проверили без GitHub

У репозитория пока нет удалённой копии, поэтому настоящего запуска ещё не было. Что сделали вместо этого:

- **`actionlint`** проверил синтаксис workflow и ссылки на выражения.
- **Чистый клон**: тот же порядок команд в новой копии с пустой PostgreSQL и без `.env`.

```text
pnpm install --frozen-lockfile    ok, и husky подключился сам
pnpm lint / format:check          ok
pnpm typecheck / test             ok
migrate и seed на пустой базе     ok
e2e API и контракт                ok
сборка сайта и Playwright         3 passed
git status после всех шагов       0 изменений
```

Чего это не доказывает: прогон шёл на Windows, а CI работает на Linux, и сами действия GitHub не запускались. Окончательный ответ даст только первый настоящий запуск.

### Как защитить main

Сам по себе CI только показывает результат. Чтобы красный коммит не попал в `main`, нужно правило защиты ветки в настройках репозитория: required status checks. Настраивается один раз после первого запуска.

## Ещё раз, что мы сделали

Описали три задания: быстрые проверки, сквозные тесты с настоящей базой и браузером и подъём всего проекта в Docker. Токену оставили только чтение. Настоящего запуска пока не было, поэтому проверили workflow через `actionlint` и повторили все шаги в чистом клоне. Кайф: проект больше не зависит от того, что случайно лежит у тебя на диске.

## Вопросы на собеседовании

**Что такое CI, и чем отличается от CD?**
CI автоматически проверяет каждое изменение: сборка и тесты на чистой машине. CD автоматически доставляет проверенные изменения в окружение. У нас пока только CI.

**Почему `pnpm install --frozen-lockfile`?**
Установка падает, если lockfile не соответствует `package.json`. Без этого CI мог бы проверять не те версии, что закоммичены.

**Почему тесты в CI идут на настоящей базе, а не на моках?**
Мок не поймает ошибку в миграции, SQL или ограничениях базы. Контейнер PostgreSQL поднимается за секунды и даёт то же поведение, что в проде.
