# 02. NestJS, Prisma и PostgreSQL в Docker

## Что сделали

Подняли `apps/api` на NestJS, подключили его через Prisma к PostgreSQL в Docker и сделали эндпоинт `GET /api/v1/health`, который честно проверяет связь с базой.

## Что и зачем

| Файл | Зачем нужен |
| --- | --- |
| `compose.yaml` | PostgreSQL 18 одной командой, доступный только с этой машины |
| `apps/api/prisma/schema.prisma` | Описание таблиц. Пока одна: `ContactMessage`, её заюзает форма контактов |
| `apps/api/prisma/migrations/` | SQL-миграции. Коммитятся, это история схемы базы |
| `apps/api/prisma7.config.ts` | Настройки Prisma CLI: где схема и куда подключаться |
| `src/prisma/*` | `PrismaService`: клиент базы как провайдер Nest |
| `src/health/*` | Эндпоинт проверки здоровья и его unit-тест |
| `src/app.setup.ts` | Общая настройка приложения для `main.ts` и e2e-тестов |
| `test/health.e2e-spec.ts` | Настоящий HTTP-запрос через supertest и настоящая база |

Команды:

```bash
pnpm db:up                     # docker compose up -d --wait
pnpm db:migrate --name init    # создал и применил первую миграцию
pnpm dev:api                   # shared + API в режиме watch
pnpm test                      # unit-тесты
pnpm test:e2e                  # e2e, нужна запущенная база
```

Почему именно так, и какие были альтернативы:

- **Prisma против TypeORM и Drizzle.** Так решили в стеке проекта: схема в одном файле, типы генерируются, миграции из коробки. Цена: шаг `prisma generate` и зависимость от своего CLI.
- **Docker против локального PostgreSQL.** Контейнер даёт одну и ту же версию на любой машине и в CI, ничего не засоряя в системе.
- **Логин и пароль прямо в `compose.yaml`.** Для локальной базы это не секрет, а порт открыт только на `127.0.0.1`. Лишний `.env` здесь ничего бы не защитил. В проде настройки придут из переменных хостинга.
- **Свой `/health` против `@nestjs/terminus`.** Нам нужна одна проверка, а это пять строк. Понадобится больше проверок, тогда и возьмём Terminus.
- **`ContactMessage` как первая таблица.** Prisma без моделей генерировать клиент нечего, а эта таблица всё равно нужна в v1. Статусы сообщений добавим в v2.

### Где разошлись с генератором

`nest new` сейчас создаёт ESM-проект с Vitest и oxlint, а у нас в стеке ESLint. Поэтому oxlint и Prettier убрали до отдельного шага про качество кода. Заодно снесли `@nestjs/mau` и скрипт `deploy`: деплоить будем не на их платформу.

Ещё два сюрприза:

- **TypeScript 7 пришлось откатить на 6.0.3.** Прогноз из шага 01 сбылся: `@nestjs/swagger` требует `^5.5 || ^6`, а `ts-jest`, который мы тогда пробовали, требует `<7`. Поменяли одну строку в каталоге, кайф.
- **`prisma init` сам добавил агентские скиллы** в `.agents`, `.claude`, `.windsurf` и `skills-lock.json`. Удалили: проекту они не нужны. Вывод простой: после генераторов смотри `git status`.

## Как это работает

### Ловушка с версией Prisma

```bash
# ❌ так не работает
pnpm add -D prisma@latest
pnpm add @prisma/client@latest
```

Смотрим реестр: `prisma` с тегом `latest` это `8.0.0-rc.30`, а `@prisma/client` с тем же тегом это `7.10.1`. Разные мажорные версии, причём одна из них release candidate. Документация NestJS об этом прямо предупреждает.

**Тег распространения** (dist-tag) это имя, которое указывает на конкретную версию пакета в реестре. Простыми словами: `latest` не значит «самая стабильная», это просто ярлык, который мейнтейнер может повесить на что угодно.

```bash
# ✅ обе половинки одной и той же версии
pnpm add -D prisma@7.10.1
pnpm add @prisma/client@7.10.1
```

### Откуда берётся клиент

Prisma: «ты описал модель в схеме, я выплюну под неё TypeScript-код в `src/generated/prisma`». Этот код лежит в `.gitignore`, поэтому после свежего клона его ещё нет. Важный, преважный момент: скрипт `build` у нас `prisma generate && nest build`, иначе сборка упадёт на импорте.

```ts
// ❌ так не работает: в Prisma 7 клиенту нужен драйвер
const prisma = new PrismaClient();
```

**Драйвер-адаптер** (driver adapter) это объект, через который Prisma ходит в базу с помощью конкретной JS-библиотеки. Простыми словами: наш запрос Prisma превращает в SQL, отдаёт в `PrismaPg`, а тот выполняет его через пакет `pg` и его пул соединений.

```ts
// ✅
const adapter = new PrismaPg({ connectionString: url });
const prisma = new PrismaClient({ adapter });
```

### Почему не new PrismaClient в каждом контроллере

```ts
// ❌ у каждого контроллера свой клиент и свой пул соединений
export class HealthController {
  private prisma = new PrismaClient({ adapter: createAdapter() });
}
```

Контроллеров станет пять, и пулов соединений станет пять. Закрывать их при остановке тоже некому, а в unit-тесте базу не подменишь.

**Внедрение зависимостей** (Dependency Injection) это когда класс не создаёт зависимость сам, а получает её через конструктор. Простыми словами: при старте Nest читает типы параметров конструктора, один раз создаёт `PrismaService` и передаёт один и тот же объект всем, кто его попросил.

```ts
// Упрощённая модель - не исходный код NestJS
const container = new Map<unknown, unknown>();

function resolve(token) {
  if (!container.has(token)) {
    // типы параметров сохранил emitDecoratorMetadata при компиляции
    const paramTypes = Reflect.getMetadata('design:paramtypes', token) ?? [];
    const args = paramTypes.map(resolve);
    container.set(token, new token(...args)); // создаётся один раз
  }
  return container.get(token);
}

resolve(HealthController);
// PrismaService нужен ConfigService -> создали ConfigService,
// затем PrismaService, затем HealthController
```

Как наш код с этим местом взаимодействует:

```ts
// ✅ просим зависимость, а создаёт её Nest
constructor(private readonly prisma: PrismaService) {}
```

Отсюда важное следствие: для DI этот импорт нужен в рантайме, поэтому в контроллере написано `import { PrismaService }`, а не `import type`. Тип из `import type` при компиляции исчезает, и Nest не узнал бы, что внедрять. Взяли и запомнили: **в конструкторах провайдеров Nest импортируй класс обычным импортом**.

Хуки `onModuleInit` и `onModuleDestroy` Nest вызывает при старте и остановке. А `app.enableShutdownHooks()` в `main.ts` заставляет его реагировать на сигналы вроде `SIGTERM`, иначе `$disconnect()` при остановке контейнера не вызовется.

### Как работает /health

```ts
// ❌ так не работает: ответит ok, даже если база лежит
@Get()
check() {
  return { status: 'ok' };
}
```

Такой эндпоинт проверяет только то, что процесс Node жив. Поэтому мы реально спрашиваем базу через `SELECT 1`, а при ошибке пишем причину в лог и отвечаем `503 Service Unavailable`. Клиенту детали подключения не отдаём.

Это проверено на собранном приложении, запущенном через `node dist/main.js`:

```text
база работает:   {"status":"ok","database":"up"}  HTTP 200
база остановлена: {"message":"База данных недоступна", ...}  HTTP 503
база вернулась:  {"status":"ok","database":"up"}  HTTP 200
```

Перезапускать API после возврата базы не пришлось: пул сам установил новое соединение.

### Почему появился configureApp

```ts
// ❌ префикс задан только в main.ts
const app = await NestFactory.create(AppModule);
app.setGlobalPrefix('/api/v1');
```

E2E-тест не вызывает `main.ts`, он собирает приложение сам через `Test.createTestingModule`. Значит, в тесте префикса не было бы, и тест проверял бы не то приложение, что уедет в прод.

```ts
// ✅ одна функция для main.ts и для тестов
export function configureApp(app: INestApplication): void {
  app.setGlobalPrefix(API_PREFIX); // константа из @portfolio/shared
}
```

Это ещё и первое реальное использование `packages/shared`: фронт позже возьмёт оттуда же этот префикс.

### Почему Vitest, а не Jest

Сначала мы честно поставили Jest и получили вот что:

```bash
# ❌ работает, но держится на флаге и лишней настройке
node --experimental-vm-modules node_modules/jest/bin/jest.js
# ExperimentalWarning: VM Modules is an experimental feature
```

Наш проект в ESM, поэтому импорты пишутся с расширением: `./health.module.js`. Jest смотрит на диск, файла `.js` там нет, пришлось писать `moduleNameMapper`. Поддержка ESM в Jest до сих пор экспериментальная, а глобального объекта `jest` в этом режиме нет.

```bash
# ✅ Vitest понимает ESM и TypeScript из коробки
vitest run
```

Vitest: «дай мне `.ts`, я сам его преобразую через Vite и разберусь с `.js` в импортах». И раннер на весь проект теперь один, на фронте тоже будет Vitest.

Важный, преважный момент: Nest при старте читает типы параметров конструктора из метаданных декораторов (`emitDecoratorMetadata`). Многие быстрые трансформеры эти метаданные не выдают, и тогда DI падает. Наш e2e-тест собирает настоящий `AppModule` с настоящим `PrismaService`, поэтому он сразу показал бы такую поломку. Тест прошёл без SWC и дополнительных плагинов.

### migrate dev против migrate deploy

**Миграция** (migration) это SQL-файл, который переводит схему базы из одного состояния в другое. Простыми словами: Prisma сравнивает `schema.prisma` с историей миграций, пишет разницу в `migration.sql`, применяет файл и отмечает это в служебной таблице `_prisma_migrations`.

- `prisma migrate dev` только для разработки: создаёт новые миграции и может предложить сбросить базу.
- `prisma migrate deploy` для прода: только применяет уже закоммиченные файлы.

Запусти `migrate dev` на проде, и он может попытаться снести базу с реальными данными. Взяли и запомнили: **в проде только `migrate deploy`**.

```yaml
# ❌ порт открыт на всех сетевых интерфейсах
```

## Ещё раз, что мы сделали

Подняли PostgreSQL через `compose.yaml`, сгенерировали каркас `nest new` и убрали из него лишнее. Поставили Prisma 7, обходя ловушку с тегом `latest`, описали первую модель и применили миграцию. Обернули клиент в `PrismaService`, чтобы Nest создавал его один раз и сам закрывал. Поверх сделали `/api/v1/health`, покрыли unit- и e2e-тестами, а затем вживую уронили базу и увидели 503 и восстановление. Погнали к контенту.

## Вопросы на собеседовании

**Зачем нужен `PrismaService`, почему не обычный экспорт клиента из файла?**
Провайдер встраивается в DI: Nest создаёт его один раз, вызывает хуки подключения и отключения, а в тесте его легко подменить. Глобальный экспорт дал бы один экземпляр, но управлять его жизненным циклом и подменять его пришлось бы вручную.

**Чем `migrate dev` отличается от `migrate deploy`?**
`dev` создаёт миграции и может предложить сброс базы, поэтому он только для разработки. `deploy` лишь применяет уже закоммиченные миграции и подходит для прода и CI.

**Что должен проверять health-эндпоинт?**
Минимум то, без чего сервис не работает, у нас это база. При отказе отвечаем 503, чтобы балансировщик или платформа могли это увидеть. Детали ошибки пишем в лог, наружу не отдаём.
