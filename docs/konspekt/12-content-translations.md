# 12. Контент на двух языках: таблицы переводов и `?locale=`

## Что сделали

Научили базу хранить тексты на русском и английском, а API отдавать их по параметру `?locale=`, причём старые клиенты без параметра продолжают работать.

## Что и зачем

| Файл | Что изменилось |
| --- | --- |
| `prisma/schema.prisma` | Enum `Locale`, четыре таблицы `*_translations`, поле `linkedinUrl` |
| `prisma/migrations/...content_translations` | Миграция, написанная вручную: переносит данные, а потом удаляет старые колонки |
| `packages/shared/src/locale.ts` | Список языков и Zod-схема параметра, общие для сайта и API |
| `src/common/locale-query.ts` | Декораторы `@LocaleQuery()`, `@ApiLocaleQuery()` и функция `singleTranslation` |
| `src/database/seed-data.ts` | Тексты на двух языках, английские взяты из английского резюме |

Почему именно так, и какие были альтернативы:

- **Таблицы переводов против копии строки на язык.** С копиями дата работы и стек хранились бы дважды и могли разойтись. Цена таблиц: на один запрос приходится больше кода.
- **Таблицы переводов против JSON-колонки.** JSON проще в схеме, но база не проверит, что перевод заполнен, а в админке v2 такие поля неудобно менять.
- **`?locale=` против заголовка `Accept-Language`.** Параметр явный, его видно в логах и Swagger, а ещё он прямо попадает в ключ кэша Next.js.
- **Названия навыков без перевода.** TypeScript и React на всех языках одинаковые. Единственное исключение, «Микрофронтенды», заменили на Microfrontends.

## Как это работает

### Почему нельзя просто добавить колонки

Наивный вариант напрашивается сам:

```prisma
// ❌ на каждый язык и каждое поле по колонке
model Project {
  nameRu        String
  nameEn        String
  descriptionRu String
  descriptionEn String
}
```

Третий язык означает новую миграцию и правку всех запросов. Кроме того, код начинает собирать имя поля из строки: `project['name' + suffix]`. Типы тут уже ничем не помогут.

**Таблица переводов** (translation table) это отдельная таблица с текстами и составным ключом из записи и языка. Простыми словами: одна строка `projects` и по одной строке в `project_translations` на каждый язык. Взяли и запомнили.

```text
projects                        project_translations
id | slug         | stack       project_id | locale | name         | description
1  | paint-online | {React}     1          | ru     | Paint Online | Совместный...
                                1          | en     | Paint Online | Collaborative...
```

`@@id([projectId, locale])` запрещает на уровне базы второй перевод на тот же язык.

### Как Prisma выбирает нужный перевод

```ts
const projects = await prisma.project.findMany({
  select: {
    slug: true,
    translations: { where: { locale }, select: { name: true } },
  },
});
// [{ slug: 'paint-online', translations: [{ name: 'Paint Online' }] }]
```

Клиенту API незачем знать, как устроена база, поэтому сервис разворачивает массив в плоский объект:

```ts
return projects.map(({ translations, ...project }) => ({
  ...project,
  ...singleTranslation(translations),
}));
```

Функция `singleTranslation` бросает ошибку, если перевода нет. Лучше ответ 500, чем страница с `undefined` вместо заголовка.

### Почему миграцию написали руками

Prisma посмотрел на схему и предложил просто удалить колонки. Заодно он предупредил, что в них лежат данные:

```sql
-- ❌ что выплюнул бы автоматический вариант: тексты пропадут
ALTER TABLE "projects" DROP COLUMN "name";
```

Поэтому порядок задаём сами: создать таблицы, скопировать данные, и только потом удалить колонки.

```sql
-- ✅ существующие строки становятся русской версией
INSERT INTO "project_translations" ("project_id", "locale", "name", "description")
SELECT "id", 'ru', "name", "description" FROM "projects";

ALTER TABLE "projects" DROP COLUMN "name", DROP COLUMN "description";
```

Важный, преважный момент: как проверить, что ручная миграция совпала со схемой. Погнали сравнивать:

```bash
prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code
# No difference detected
```

### Как компилятор ловит пропущенный перевод

```ts
function toRows<T extends object>(translations: Record<Locale, T>) {
  return LOCALES.map((locale) => ({ ...translations[locale], locale }));
}

// ❌ не скомпилируется: нет ключа en
toRows({ ru: { name: 'Языки' } });
```

`Record<Locale, T>` требует ключ на каждый язык. Добавишь третий язык в `LOCALES`, и TypeScript покажет все тексты, где его не хватает. Кайф.

### Что происходит при выкладке

Параметр необязательный, и без него API отдаёт русский. Значит, старый сайт на Vercel не сломается от нового API. Но у миграции есть честный минус:

```text
1. Pre-deploy применил миграцию: старых колонок больше нет
2. Старый API ещё работает и читает эти колонки: запросы контента падают
3. Новый API стартовал: всё снова работает
```

На несколько секунд API контента отвечает ошибками. Посетителю это не видно, потому что страницы отдаются из кэша. В системе, где простой недопустим, миграцию разбили бы на две выкладки: сначала добавить новое, потом удалить старое. Этот приём называется expand and contract.

## Ещё раз, что мы сделали

Вынесли тексты в таблицы переводов, а даты, ссылки и стек оставили в основных. Написали миграцию, которая превращает существующие строки в русскую версию, и сверили её со схемой. Добавили `?locale=` с проверкой через общую Zod-схему: неизвестный язык получает 400. Заполнили английские тексты и обновили контракт OpenAPI.

## Вопросы на собеседовании

**Как хранить многоязычный контент в реляционной базе?**
Чаще всего в таблице переводов с составным ключом из записи и языка. Общие поля не дублируются, а новый язык не требует менять схему. Альтернативы: колонка JSON или отдельная строка на язык, у них свои компромиссы.

**Почему нельзя всегда доверять автоматической миграции?**
Инструмент видит только разницу схем и не знает, что данные надо перенести. Переименование или перенос колонки он может выразить как удаление и создание, а это потеря данных.

**Что такое expand and contract?**
Способ менять схему без простоя. Сначала добавляем новое, и старая версия кода продолжает работать. Затем выкладываем новый код, переносим данные, и только в последней выкладке удаляем старое.
