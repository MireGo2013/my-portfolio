# 04. Next.js: статическая страница и типы из OpenAPI

## Что сделали

Подняли `apps/web` на Next.js 16 и собрали главную страницу статически из данных API, причём типы ответов генерируются из контракта API, а не пишутся руками.

## Что и зачем

| Файл | Зачем нужен |
| --- | --- |
| `apps/api/src/export-openapi.ts` | Выгружает контракт в `apps/api/openapi.json` без запуска сервера и базы |
| `apps/web/src/lib/api/schema.d.ts` | Типы, сгенерированные `openapi-typescript` из контракта |
| `apps/web/src/lib/api/content-api.ts` | Типизированный клиент на `openapi-fetch`. Про кэш и Next.js не знает |
| `apps/web/src/lib/content.ts` | Функции для страниц: добавляют кэш, работают только на сервере |
| `apps/web/next.config.ts` | Cache Components и наш профиль кэша `content` |
| `apps/web/src/components/hero.tsx` | Первый экран |

Команды:

```bash
pnpm gen:api    # код API -> openapi.json -> schema.d.ts
pnpm dev:web    # сайт в режиме разработки, нужен запущенный API
pnpm build      # сборка всего, для сборки сайта API должен работать
pnpm test       # unit-тесты API и сайта
```

Почему именно так, и какие были альтернативы:

- **Контракт файлом в репозитории против запроса к живому серверу.** Иначе типы фронта зависели бы от запущенного API, а изменения контракта не были бы видны в diff. Цена: файл надо обновлять. Поэтому e2e-тест падает, если `openapi.json` разошёлся с кодом.
- **`use cache` против `export const revalidate`.** В Next 16 рекомендована модель Cache Components, а `revalidate` документация относит к предыдущей модели. Плюс `cacheTag` пригодится для обновления страниц из админки в v2.
- **Tailwind через `@tailwindcss/postcss`.** Генератор поставил `@tailwindcss/turbopack`, и с ним `next build` у нас завис на компиляции больше чем на 6 минут. С PostCSS сборка занимает секунды. Механизм зависания внутри лоадера не выясняли: заменили и проверили результат.
- **`agentRules: false`.** Иначе Next создаёт в проекте `AGENTS.md` для ИИ-агентов. Проверили: `next dev` его больше не создаёт.

Предупреждение, которое мы оставили осознанно: `openapi-typescript` объявляет peer `typescript ^5.x`, а у нас 6.0.3. Типы при этом генерируются правильно, что подтверждают `tsc` и e2e-проверка контракта. При обновлении генератора стоит глянуть, не сняли ли это ограничение.

## Как это работает

### Почему не руками писать типы

```ts
// ❌ так не работает надёжно: тип живёт отдельно от API
type Experience = { startDate: string; endDate: string };
```

На бэке `endDate` может быть `null`, а тип об этом не знает. TypeScript молчит, и `endDate.slice()` падает уже у пользователя.

**`openapi-typescript`** читает OpenAPI-документ и выплёвывает TypeScript-типы. Простыми словами: это обычный скрипт, который на входе берёт JSON, а на выходе пишет `.d.ts`. В рантайме его нет.

**`openapi-fetch`** это тонкая обёртка над `fetch`, которая по этим типам знает пути и формы ответов.

```ts
// Упрощённая модель - не исходный код openapi-fetch
function createClient<Paths>({ baseUrl }: { baseUrl: string }) {
  return {
    // типы подсказывают путь и форму data, а в рантайме это обычный fetch
    async GET<P extends keyof Paths>(path: P) {
      const response = await fetch(baseUrl + String(path));
      if (response.ok) return { data: await response.json(), response };
      return { error: await response.json().catch(() => undefined), response };
    },
  };
}
```

Как наш код с этим взаимодействует:

```ts
const { data, response } = await client.GET('/api/v1/profile');
// опечатка в пути не скомпилируется, а data имеет тип ProfileDto | undefined
if (!data) throw new Error(`GET /profile: API ответил ${response.status}`);
```

Важный, преважный момент: `openapi-fetch` не бросает ошибку на ответ 500, он её возвращает. Если её не проверить, страница соберётся пустой. Именно поэтому мы бросаем ошибку сами, и тесты на MSW это закрепляют.

Весь поток выглядит так. Взяли и запомнили:

```text
DTO в NestJS -> openapi.json -> schema.d.ts -> client.GET(...) -> компонент
```

Меняешь поле в DTO, запускаешь `pnpm gen:api`, и TypeScript сам показывает все места на фронте, которые нужно поправить.

### Как выгрузить контракт без базы

```ts
// ❌ так не работает: нужны база и DATABASE_URL только ради JSON-файла
const app = await NestFactory.create(AppModule);
```

Конструктор `PrismaService` требует `DATABASE_URL`. В CI это лишняя настройка.

```ts
// ✅ preview строит граф модулей, не создавая провайдеры
const app = await NestFactory.create(AppModule, { preview: true, logger: false });
```

Проверили: временно убрали `.env`, и экспорт отработал. Скрипт запускается из собранного `dist`, а не через `tsx`: `esbuild` внутри `tsx` не выдаёт метаданные декораторов, на которых держится Nest.

### Что такое статическая страница в Next 16

Next.js: «я выполню страницу на этапе сборки. Если всё можно получить заранее, сохраню готовый HTML».

```tsx
// ❌ сборка упадёт: данные без кэша и без Suspense
export default async function HomePage() {
  const profile = await fetch(url).then((r) => r.json());
  return <Hero profile={profile} />;
}
```

При включённых Cache Components Next требует явного решения: кэшировать данные или отдавать их потоком во время запроса.

**`use cache`** это директива, которая кэширует результат функции. Простыми словами: компилятор Next оборачивает функцию так, что результат сохраняется по ключу из её идентификатора и аргументов. Если это случилось на сборке, результат попадает прямо в HTML.

```ts
// ✅
export async function getProfile(): Promise<Profile> {
  'use cache';
  cacheLife('content');
  cacheTag('profile');
  return contentApi().getProfile();
}
```

```ts
// Упрощённая модель - не исходный код Next.js
function useCacheWrapper(id, fn) {
  return async (...args) => {
    const key = JSON.stringify([id, args]);
    const entry = store.get(key);
    if (!entry) return save(key, await fn(...args));
    if (isOlderThan(entry, 'expire')) return save(key, await fn(...args)); // ждём
    if (isOlderThan(entry, 'revalidate')) {
      fn(...args).then((value) => save(key, value)).catch(logError); // в фоне
    }
    return entry.value; // отдаём сразу, даже устаревшее
  };
}
```

### Ловушка с expire

Сначала мы взяли готовый профиль `cacheLife('hours')`. У него `revalidate` 1 час, а `expire` 1 день.

```text
❌ Сутки никто не заходил (для портфолио обычное дело)
   -> следующий посетитель ждёт ответа API
   -> API заснул или упал, и рекрутер видит медленную страницу или ошибку
```

Поэтому завели свой профиль:

```ts
// ✅ next.config.ts
cacheLife: {
  content: { stale: 300, revalidate: 3600, expire: 60 * 60 * 24 * 365 },
},
```

Три поля значат вот что. `stale` это сколько браузер не спрашивает сервер. `revalidate` это через сколько следующий запрос запустит обновление в фоне. `expire` это через сколько без посещений следующий запрос будет ждать свежие данные.

Вторая ловушка: `stale` меньше 30 секунд исключает данные из пререндера. Мы на это наступили в тесте с `stale: 1`, и сборка упала.

### Что мы проверили руками

Без реальной проверки это были бы просто красивые слова, поэтому прогнали:

```text
Сборка без API:     упала за 8 секунд с ECONNREFUSED. Пустой сайт не опубликуется.
Сборка с API:       ○ /  Revalidate 1h  Expire 1y
API выключен:       страница отдаётся, 200, x-nextjs-cache: HIT
```

И отдельно фоновое обновление, с временным `revalidate: 3`:

```text
исходно             Владислав Соболь   200
поменяли базу:
  первый запрос     Владислав Соболь   200   <- старое, запускает обновление
  следующий         ОБНОВЛЕНО          200   <- кайф, новое
выключили API:
  запрос            ОБНОВЛЕНО          200   <- последняя удачная версия
  ещё запрос        ОБНОВЛЕНО          200   <- ошибка только в логах
```

Отсюда важное свойство: упавший API не роняет сайт, а просто останавливает обновление контента.

### Почему API_URL без NEXT_PUBLIC_

Переменные с `NEXT_PUBLIC_` Next вшивает в код для браузера. Наш `API_URL` нужен только серверу, а `import 'server-only'` в `content.ts` остановит сборку, если этот файл случайно импортируют из клиентского компонента. Проверили: адреса API в HTML нет.

### Тесты: что и чем

- `content-api.test.ts` проверяет клиент через **MSW** (Mock Service Worker). Простыми словами: MSW перехватывает `fetch` внутри процесса теста и отвечает как настоящий сервер, поэтому `openapi-fetch` работает по-настоящему. В MSW 3 опция называется `onUnhandledFrame`, а не `onUnhandledRequest`.
- `hero.test.tsx` рендерит компонент через **React Testing Library** в jsdom и ищет элементы так, как их видит пользователь: по ролям и тексту.

Сами `use cache` и страницу Vitest не проверит: это работа компилятора Next. Их покрыли ручные проверки выше, а автоматические появятся вместе с Playwright.

## Вопросы на собеседовании

**Что будет с сайтом, если API упадёт?**
Уже собранные страницы продолжат открываться, потому что это готовый HTML. Фоновое обновление завершится ошибкой, она попадёт в лог, а посетители увидят последнюю удачную версию. Новая сборка при этом упадёт, и это намеренно, чтобы не опубликовать пустой сайт.

**Чем отличаются `revalidate` и `expire`?**
После `revalidate` следующий запрос получает старые данные сразу, а обновление идёт в фоне. После `expire` без посещений запрос ждёт свежие данные синхронно. Поэтому для редко посещаемого сайта мы сделали `expire` очень длинным.

**Как фронт узнаёт о ломающем изменении API?**
Контракт лежит в репозитории, а типы генерируются из него. Изменение DTO без обновления `openapi.json` роняет e2e-тест, а после обновления `tsc` показывает все места на фронте, которые надо поправить.
